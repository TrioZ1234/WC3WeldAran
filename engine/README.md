# engine — рантайм

Реализация контракта из 321 функции, поверх которого без изменений работает
оригинальный `war3map.j`. Этап 3 дорожной карты.

## Запуск

```bash
python3 tools/fetch_war3_data.py                 # один раз: common.j, Blizzard.j, таблицы SLK
node engine/cli/run-jass.ts build/extracted/war3map.j
node engine/cli/run-jass.ts build/extracted/war3map.j --json docs/data/jass-runtime.json
node engine/cli/run-jass.ts build/extracted/war3map.j --no-war3   # только скрипт карты
node engine/cli/run-game.ts --seconds 300        # запуск игры: время идёт
node engine/test/smoke.ts                        # регрессионный тест
```

Нужен Node 18+ (на 22.6+ TypeScript исполняется напрямую, сборка не требуется).
Внешних зависимостей нет.

## Порядок загрузки

VM принимает несколько скриптов и склеивает их в одну программу; при совпадении
имён побеждает более поздний — ровно как в Warcraft III.

| Файл | Что даёт |
|---|---|
| `common.j` | 1 160 деклараций нативных функций, 91 тип хендла, 426 констант |
| `Blizzard.j` | 923 готовые функции — все обёртки `*BJ` |
| `war3map.j` | 1 018 функций логики карты |

Это решение стоит объяснить отдельно. Обёртки `*BJ` — обычный JASS, и писать
их руками означало бы воспроизводить чужой код с риском разойтись в мелочах.
Загрузка оригинального `Blizzard.j` убирает 46 функций из контракта и делает
их поведение точным по построению. А декларации из `common.j` дают заглушкам
объявленный тип возврата: `integer` возвращает 0, а не `null`, и арифметика
не ломается. Неизвестных констант было 36 — стало 0.

## Принятые решения

**Обход дерева, а не байткод.** Архитектура предполагает байткод, и это
правильная цель. Но интерпретатор по дереву доводит `main()` до конца в разы
быстрее по срокам разработки и уже сейчас даёт лог порядка вызовов, ради
которого этап 3 и затевался. Компилятор в байткод встанет за тот же интерфейс,
когда контракт устоится, а профилировщик покажет, что узкое место здесь.

**`and` и `or` вычисляют оба операнда.** JASS не делает короткого замыкания,
и карты пишутся с учётом этого. Отклонение здесь ломает сценарии тихо.

**Целочисленное деление честное.** `7 / 2` — это 3 для целых и 3.5 для
вещественных. Значения носят с собой свой тип именно поэтому: ошибка в этом
месте незаметно портит арифметику урона и золота.

**Заглушки возвращают объявленный тип, а не `null` наугад.** Тип берётся из
декларации в `common.j`: `integer` даёт 0, `boolean` — false, а хендл всё же
`null`, иначе `loop exitwhen FirstOfGroup(g)==null endloop` крутится вечно.
Никогда не свежий хендл — это самая частая причина зависания.

**ГПСЧ детерминированный, `Math.random` под запретом.** Lockstep на 12 игроков
требует одинаковой последовательности на всех клиентах — это условие
закладывается сразу, а не «потом».

## Игра идёт

`main()` больше не конец. После него запускаются часы, и карта начинает жить
сама:

```
simulated 300s of game time in 766 ms   =   392x реального времени
  тиков                9 600 при 32 Гц
  срабатываний таймеров 66 760
  вычислений триггеров   9 959
  инструкций          1 172 287
  ошибок                     0
```

Главное доказательство — **карта сама порождает юниты**: 2 310 после `main()`,
2 394 к первой минуте. 84 юнита 14 типов, включая `h01S`, `h01V`, `h01U` —
это её собственная логика старта, сработавшая по таймеру.

### Корутины

`TriggerSleepAction` приостанавливает поток посреди выражения и возобновляет
его через нужное число тиков. Это не удобство, а необходимость: `PolledWait`
в `Blizzard.j` — цикл, который двигается только за счёт сна внутри себя.
Синхронный обходчик там крутится вечно.

Реализовано через генераторы JS: весь путь исполнения — `execStmt`, `evalExpr`,
`callFunction` — это генераторы, а `TriggerSleepAction` делает `yield`. Разница
измерима: до корутин один зависший `PolledWait` сжигал 50 миллионов инструкций
и валил прогон; после — 136 тысяч инструкций и ноль ошибок.

Сон внутри колбэка нативной функции (условие, фильтр) не приостанавливает
поток, а считается пропущенным — Warcraft III ведёт себя так же.

### Бюджет на поток, а не на мир

Счётчик инструкций у каждого потока свой. Один разогнавшийся цикл убивает
себя, а не всю симуляцию, и попадает в `tickErrors` с именем функции и строкой.

## Бой

Юниты, которые спавнит сама карта, теперь дерутся:

```
60 с игрового времени, 19.8x реального
  юнитов на поле 2 347   живых 2 312
  атак            8 764
  смертей            35
  урона          71 164
```

Характеристики берутся из `build/data/resolved/units.json` — то есть из
разрешённых объектных данных, где известны и ваши правки, и унаследованное
от прототипов. Таблица «тип атаки против типа брони» читается из **вашего**
`war3mapMisc.txt`, а не из умолчаний Blizzard: у вас pierce против лёгкой
брони даёт 2.10, а не стоковые 2.00.

Формула брони — как в Warcraft III: 6 % за очко с убывающей отдачей, то есть
10 брони гасит 37 %, а отрицательная броня усиливает урон.

Отдельный стенд для проверки баланса:

```bash
node engine/cli/run-battle.ts --a h01S --b h01V --count 10
node engine/cli/run-battle.ts --list
```

### Тот же бой в браузере

```bash
python3 tools/make_battle_demo.py     # -> build/battle.html
```

`demo/battle.html` — шаблон страницы, он лежит в git. Сама страница не лежит:
сборщик подставляет в неё характеристики юнитов, таблицу урона карты и иконки,
декодированные из BLP, а иконки — собственность Blizzard. Шаблон в репозитории,
данные у каждого свои.

Симуляция на странице — порт `sim/{fixed,combat,units}.ts` на чистый JS с той же
целочисленной арифметикой. Множители сходятся с движком до третьего знака
(`normal → hero` 0.699, `magic → hero` 0.301), и страница сама проверяет
детерминизм повтором боя при загрузке.

### Детерминизм проверяется, а не декларируется

`run-battle.ts` после боя прогоняет тот же бой заново и сравнивает число атак,
смертей и суммарный урон. Расхождение — провал. Это же проверяет
регрессионный тест. Без этого свойства не будет lockstep на 12 игроков,
и обнаружить его потерю надо в тот же день, а не через полгода.

Поэтому в симуляции нет ни `Math.random`, ни плавающей арифметики, ни
`Math.sqrt`: корень целочисленный, по Ньютону.

### Пространственный индекс

Три тысячи юнитов на карте 61 440 x 61 440 — это девять миллионов проверок
дистанции за тик, если перебирать пары. Равномерная сетка сводит запрос
к тем ячейкам, которые реально попадают в радиус агро.
