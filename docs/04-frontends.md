# 04 — Два клиента: web и Godot

Решение по стеку принято: **TypeScript + WebGPU** как основной движок,
**Godot 4** как путь к нативной сборке. Документ описывает, как удержать это
от превращения в две разные игры.

---

## 1. Риск, который надо признать сразу

Два клиента — это два рендера, два цикла ввода, два набора багов. Если пустить
на самотёк, через полгода получится две несовместимые версии, и любая правка
баланса будет делаться дважды.

Поэтому граница проводится жёстко и с самого начала.

## 2. Что общее, а что нет

```
┌──────────────────────────────────────────────────────────┐
│  ОБЩЕЕ — один источник, ноль дублирования                │
│                                                          │
│  tools/            конвейер (Python)                     │
│  build/data/       terrain.bin, *.json                   │
│  build/assets/     *.glb, *.webp, *.jpg                  │
│  контракт из 321 функции                                 │
│  ядро симуляции + JASS VM   ← см. раздел 4               │
├──────────────────────────────────────────────────────────┤
│  РАЗНОЕ — только представление                           │
│                                                          │
│  web/    рендер WebGPU, ввод, HUD                        │
│  godot/  рендер Godot, ввод, HUD                         │
└──────────────────────────────────────────────────────────┘
```

Правило простое: **клиент не имеет права ничего выводить из карты сам.**
Ни один из них не открывает `.w3x`. Оба читают готовый результат конвейера.
`build.py` публикует одни и те же каталоги в `web/public/` и `godot/`
ссылками — физически это одна копия на диске, разойтись нечему.

glTF и WebP выбраны не случайно: Godot импортирует их штатно, браузер тоже.
Ни одному клиенту не нужен собственный загрузчик MDX или BLP.

## 3. Зачем вообще два

| | web | Godot |
|---|---|---|
| Распространение | по ссылке, без установки | установщик |
| Итерация | секунды | минуты |
| Пик производительности | ниже | выше |
| Консоли, Steam | нет | да |
| Отладка рендера | средняя | хорошая |

Веб-клиент — рабочая лошадка разработки: правка видна мгновенно, а игроку
достаточно ссылки. Godot — то, что можно выложить в Steam.

Стоит знать про третий путь: **Tauri** заворачивает веб-клиент в нативное
приложение почти без работы. Если нужна только «сборка под Windows», Tauri
закрывает задачу дешевле, чем второй клиент. Godot оправдан, если нужны его
редактор, экспорт под консоли или нативная производительность. Это решение
можно отложить — до этапа 4 оба варианта остаются открытыми.

## 4. Главная развилка: где живёт игровая логика

Ядро (JASS VM + симуляция) обязано быть **одно**. Два ядра — это два баланса
и рассинхрон в сетевой игре.

Но на TypeScript ядро из Godot не вызвать: JS-рантайма там нет.

Варианты:

| Подход | Оценка |
|---|---|
| Ядро на **Rust** → WASM для веба, GDExtension для Godot | Рекомендуется |
| Ядро на TypeScript, Godot только как рендер поверх WASM-моста | Хрупко |
| Два ядра | Неприемлемо |

Rust компилируется и в WASM, и в нативную библиотеку. Оба клиента получают
одну и ту же симуляцию, бит в бит — что критично для lockstep.

**Что делать сейчас.** Ядро писать на TypeScript, но с самого начала:

- никакого DOM, `window`, `fetch` внутри ядра;
- никакой плавающей арифметики в боевой математике — фиксированная точка;
- никаких `Math.random` — только собственный детерминированный ГПСЧ;
- вход и выход — плоские структуры, а не объекты с методами;
- обмен с рендером через явную границу, а не общие ссылки.

При такой дисциплине перенос в Rust — механическая работа над одним модулем.
Без неё это переписывание проекта. Разница в цене — месяцы.

## 6. Проверка производительности

Веб-клиент показывает **вызовов отрисовки: 3** — ландшафт и два батча
инстансов, независимо от числа объектов. В этом вся разница с 1.26, где
25 222 декорации превращаются в тысячи вызовов за кадр.

Если на целевом железе просядет здесь, на этапе с реальными моделями станет
только хуже — и лучше узнать об этом сейчас, а не после написания движка.
