# 07 — Внешний интерфейс

До этого этапа движок было нечем запустить: скрипт карты исполнялся, время шло,
бой считался — но всё это жило в командной строке и печаталось таблицами. Здесь
описан слой, который превращает это в игру, в которую садится человек.

Ничего из движка при этом не переписано. Оболочка — надстройка: она читает тот же
результат конвейера и вызывает тот же рантайм.

---

## 1. Экраны

```
меню ──► лобби ──► загрузка ──► матч ──► результаты
  │        ▲                      │         │
  │        └──────────────────────┴─────────┘
  └──► просмотрщик мира (прежний клиент, сохранён)
```

| Экран | Файл | Что делает |
|---|---|---|
| Главное меню | `web/src/shell/screens/menu.ts` | Три входа. Сетевая игра выключена явно, с причиной в подсказке |
| Лобби | `web/src/shell/screens/lobby.ts` | 12 слотов, боты, команды, расы, правила, чат |
| Загрузка | внутри экрана матча | Прогресс по этапам: скрипты, объекты, мир |
| Матч | `web/src/shell/screens/match.ts` | Рендер, ввод, приказы, пауза |
| Результаты | `web/src/shell/screens/results.ts` | Итоги последним снимком состояния |
| Просмотрщик | `web/src/shell/screens/viewer.ts` | Прежний клиент, целиком, за пунктом меню |
| Сбой | `web/src/shell/screens/fatal.ts` | Причина и команда, которая её устраняет |

Маршрутизатор — `web/src/shell/app.ts`: один экран за раз плюс то, что экран
переживает (манифест карты и последняя настройка лобби). У экрана есть выгрузка:
у матча работает цикл кадров и живёт воркер, и потерять любой из них — значит
получить вкладку, которая считает две партии одновременно.

Фреймворка нет. Вся разметка строится помощником на сорок строк
(`web/src/shell/dom.ts`): интерфейс — это горсть экранов, состояние которых
описывается одной структурой, и фреймворк здесь не купил бы ничего, кроме
сборочного шага и зависимости, за которой надо следить.

## 2. Лобби на 12 слотов

Слоты не выдуманы: их задаёт карта. `war3map.w3i` объявляет 12 игроков и
6 команд по два, и лобби эти данные **правит, а не придумывает**. Слот, которого
в карте нет, показан серым и не открывается — форма карты должна быть видна,
включая ту часть, которую игрок менять не может.

Что настраивается в строке слота:

| Столбец | Смысл |
|---|---|
| Управление | Человек · Компьютер · Открыт · Закрыт |
| Раса | Люди, орки, нежить, ночные эльфы, случайная |
| Команда | Любая из шести, которые объявила карта |
| Сложность / гандикап | У ботов — сложность, у людей — процент от 50 до 150 |
| Готовность | Боты готовы сразу, человек — сам |

Кнопки над таблицей: **заполнить ботами** (одним нажатием занимает все свободные
слоты выбранной сложностью), убрать ботов, разбить по командам поровну, выдать
случайные расы.

Слот с пометкой «вы» защищён от любых правок управления: это игрок за этим
браузером, и отдать его нельзя ни закрытием, ни передачей боту.

### Почему старт иногда недоступен

Серая кнопка «Начать игру» ничему не учит, поэтому каждый отказ несёт свою
фразу: игроков меньше двух, все в одной команде, кто-то не готов. Проверки —
`validate()` в `web/src/game/match-config.ts`, там же предупреждения, которые не
блокируют старт (неравные команды, изменённый гандикап, свободные слоты).

### Сложность ботов — это числа, а не ярлыки

```
Слабый    гандикап  80 %   перегруппировка 45 с   волна 10 юнитов
Обычный             100 %                  25 с           7
Сильный             115 %                  12 с           5
Безумный            135 %                   5 с           3
```

Гандикап действует на сами юниты, а не на решения бота: решения карте и не нужны
сложнее (см. ниже). Характеристики копируются на юнита перед изменением — иначе
усиление одного бота усилило бы всех, потому что таблица характеристик общая на
тип юнита.

## 3. Боты

`engine/ai/army-driver.ts`, около двухсот строк. Ровно столько, сколько
предсказывал [06-product.md](06-product.md): карта делает всю содержательную
часть сама. Города раз в 90 секунд выдают владельцу отряд, а 698 вызовов
`SetUnitAcquireRange` означают, что юниты сами вступают в бой по радиусу обзора.
От движка Warcraft III требовался только **марш** — довести отряд оттуда, где он
появился, туда, где есть с кем воевать.

Водитель делает три вещи: собирает простаивающих юнитов, выбирает ближайшее
вражеское **строение** (город — это и доход противника, и его подкрепления;
погоня за юнитами даёт ботов, которые бродят), отправляет отряд туда. Дальше
работает уже перенесённая логика карты.

Никакой базы, экономики и разведки нет и не требуется.

## 4. Где что считается

```
главный поток                     воркер
─────────────                     ──────
рендер (WebGPU)      ◄── снимки ── симуляция 32 Гц
интерфейс, ввод      ── приказы ─► JASS VM + бой + боты
```

Причина разделения простая: тик исполняет скрипт карты — 16 177 строк JASS,
205 триггеров, тысячи юнитов. В главном потоке тяжёлый тик — это выпавший кадр,
причём выпадает он именно в тот момент, когда на экране интересно. Здесь рендер
держит свою частоту и рисует по последнему полученному снимку, а не ждёт нового.

Это же и есть форма, которая нужна сетевой игре: по границе уже ходят команды и
состояние, а не общие ссылки.

Границу описывает `web/src/game/protocol.ts`. Состояние переходит **плоскими
типизированными массивами**, а не объектами: три тысячи юнитов на 16 снимков в
секунду — это тот объём, при котором создание трёх тысяч объектов на снимок
уводит время в сборщик мусора.

| Файл | Роль |
|---|---|
| `web/src/game/match-config.ts` | Модель лобби и правила. Ни DOM, ни движка |
| `web/src/game/protocol.ts` | Контракт сообщений и раскладка снимка |
| `web/src/game/session.ts` | Владелец воркера со стороны интерфейса |
| `web/src/worker/sim.worker.ts` | Загрузка данных и цикл 32 Гц. Всё сетевое и браузерное — здесь |
| `web/src/worker/match-runner.ts` | Матч: VM, бой, боты. Чистый — это будущий Rust |
| `web/src/hud/hud.ts` | Ресурсы, часы, выделение, приказы, счёт |
| `web/src/hud/minimap.ts` | Миникарта: ландшафт один раз, метки каждый кадр |

`match-runner.ts` намеренно не знает ни про `fetch`, ни про DOM, ни про API
воркера — всё приходит внутрь готовыми данными. Это условие из
[04-frontends.md](04-frontends.md), при котором перенос ядра в Rust остаётся
механической работой над одним модулем.

## 5. Управление

| | |
|---|---|
| Левая кнопка | Выделение: щелчок или рамка |
| Правая кнопка | Приказ по земле |
| Средняя кнопка | Панорама |
| Alt + перетаскивание | Поворот камеры |
| Колесо | Приближение |
| W A S D, стрелки | Панорама |
| Миникарта | Щелчок — камера, правая кнопка — приказ |
| M · A · X · H | Движение · атака · стоп · удержание |
| Space | Камера к выделенному, иначе к своим войскам |
| Ctrl + E | Выделить все свои войска |
| P | Пауза |
| 1 · 2 · 4 | Скорость игры |
| Esc | Отмена приказа → снять выделение → меню |
| F10 | Меню паузы |

Приказы отданы мышью так, как это принято в жанре: левая кнопка выделяет, правая
приказывает. Поэтому панорама ушла на клавиатуру, среднюю кнопку и миникарту —
туда, где она и была в Warcraft III.

Приказ правой кнопкой отрабатывается по нажатию, а не по отпусканию: RTS,
заставляющая ждать `mouseup`, ощущается сломанной.

## 6. Что видно на экране в матче

- **Ресурсы** — золото и дерево читаются из состояния игрока, которое ведёт сам
  скрипт карты, а не из отдельного счётчика интерфейса.
- **Часы и обратный отсчёт до волны.** Отсчёт берётся из периодического таймера
  карты (`Clock.periodic()`), а не считается заново: два счётчика однажды
  разойдутся, и на экране окажется неверный.
- **Счёт по командам.** С шестью командами список по игрокам не отвечает на
  вопрос, кто выигрывает. Выбитые игроки остаются в списке зачёркнутыми — знать,
  кого уже нет, тоже часть чтения счёта.
- **Панель выделения** — характеристики ведущего юнита и портрет на каждого
  остальные, с полосой здоровья на портрете: игроку нужно увидеть, кто почти
  мёртв, а не прочитать двенадцать чисел.
- **Диагностика** — юниты, тик, миллисекунды симуляции, FPS.

## 7. Запуск без собранной карты

Карта в git не лежит, поэтому свежий клон оказался бы на пустом экране без
объяснений. Вместо этого оболочка работает и честно говорит, чего не хватает:

- в меню — какая команда собирает данные;
- в лобби — предупреждение вместо описания карты;
- в матче — постоянная пометка **тренировочный бой** в углу.

Тренировочный бой — это условные характеристики (круглые, заведомо выдуманные
числа) и синтетические спавны. Он существует, чтобы интерфейс можно было пройти
насквозь, и он **не является картой**. Настоящая партия начинается после:

```bash
python3 build.py путь/к/WFWA_v0.9.9q.w3x
python3 tools/fetch_war3_data.py     # common.j и Blizzard.j
python3 tools/export_stock.py build/war3 build/data
```

`build.py` дополнительно кладёт `war3map.j`, `war3mapMisc.txt`, `common.j` и
`Blizzard.j` в `build/data/scripts/` — браузеру они нужны по HTTP, потому что
скрипт карты исполняется в воркере.

## 8. Проверки

```bash
node engine/test/smoke.ts     # 74 проверки: VM, таймеры, потоки, события
node web/test/smoke.ts        # 34 проверки: лобби, матч, боты, детерминизм
```

Обе не требуют установки — Node исполняет TypeScript сам. Тест, которому нужен
`npm install`, — это тест, который перестают запускать.

Экраны не тестируются: headless-браузер ради двенадцати выпадающих списков стоит
дороже, чем ловит. Тестируется всё под ними — правила слотов, таблица союзов,
которую они порождают, и реальный матч под управлением ботов. Последняя проверка
самая важная: **одно зерно даёт побитово ту же партию**. Это то условие, без
которого сетевая игра на 12 человек невозможна, и проверять его надо с первого
дня, а не тогда, когда рассинхрон проявится на двадцатой минуте.

## 9. Чего ещё нет

| | Состояние |
|---|---|
| Модели вместо кубов | ⬜ ассеты сконвертированы, подстановка не подключена |
| Поиск пути | ⬜ юниты идут по прямой, `war3map.wpm` не читается |
| Способности карты | ⬜ кнопки на панели есть, отключены с подсказкой |
| Туман войны | ⬜ переключатели в лобби есть, симуляция их не учитывает |
| Сетевая игра | ⬜ этап B: lockstep, транспорт |
| Звук | ⬜ |

Переключатели, которые пока ни на что не влияют (общий обзор, открыть карту),
оставлены видимыми сознательно: они показывают форму будущей партии. Кнопки, для
которых нет реализации, выключены и объясняют почему — спрятанная функция делает
дорожную карту невидимой.
