# 02 — Архитектура движка

Документ описывает целевой рантайм. Выбор стека — открытый вопрос, он вынесен
в раздел 6 и требует решения перед началом работ над движком.

---

## 1. Опорный принцип

Анализ показал: скрипту карты нужна **321 функция движка**, а не 1900.
Это меняет постановку задачи.

> Мы не переписываем игру. Мы строим рантайм, который выполняет контракт
> из 321 функции — и оригинальная игровая логика работает поверх него.

16 177 строк JASS — это годы баланса, сюжета и правок. Переписывать их вручную
означает потерять карту и получить другую игру. Вместо этого логика остаётся
исполняемым артефактом, а мы заменяем всё, что под ней.

Практическое следствие: **порт проверяем**. Реализовали функцию — отметили в списке.
Прогресс измеряется в закрытых пунктах контракта, а не в ощущениях.


Границы жёсткие: логика не знает о рендере, симуляция не знает о JASS.

## 3. Конвейер данных (offline)

Работает уже сейчас, кроме двух конвертеров ассетов.

| Этап | Вход | Выход | Статус |
|---|---|---|---|
| Распаковка MPQ | `.w3x` | сырые файлы WC3 | ✅ |
| Таблицы данных | `w3i/w3e/doo/w3u…` | JSON | ✅ |
| Строки | `.wts` | `strings.json` | ✅ |
| Модели | `.mdx` v800 | glTF 2.0 | ⬜ |
| Текстуры | `.blp` BLP1 | PNG → KTX2 | ⬜ |
| Скрипт | `war3map.j` | AST / байткод | ⬜ |

Карта — источник правды. Вышла новая версия — конвейер прогоняется заново,
ручные правки не теряются, потому что их нет.

### Что даёт конвертация ассетов

MDX v800 → glTF: скелет, скиннинг и анимации ложатся один в один; теряются
только специфичные для WC3 узлы (partikl-эмиттеры, ribbon), их придётся
описать отдельным JSON рядом с моделью.

BLP → KTX2 (Basis Universal): сжатие остаётся на видеокарте, распаковки в RAM
не происходит. Это снимает пункт 2 из диагноза 1.26 — тот самый разрыв между
13 МБ на диске и ~200 МБ в памяти.

## 4. Рантайм

### 4.1 JASS VM

JASS — маленький язык: динамика отсутствует, типы простые, замыканий нет,
ООП нет. Интерпретатор с байткодом — задача на недели, не на месяцы.

Что учесть:
- **Хендлы.** WC3 раздаёт целочисленные идентификаторы; карта пользуется
  хеш-таблицами (`SaveInteger` — 228 вызовов). Нужен реестр хендлов с теми же
  правилами переиспользования.
- **`TriggerSleepAction`.** Кооперативная многозадачность: поток JASS засыпает
  и возобновляется. Требуются корутины (генераторы/async — по стеку).
- **Порядок исполнения.** Триггеры срабатывают в порядке регистрации.
  Отклонение ломает сценарии.

### 4.2 Симуляция

Ядро — детерминированное, с фиксированным шагом, работает без рендера
(это же позволяет гонять тесты и сервер без графики).

- Шаг фиксированный (WC3 — 1/32 с), рендер интерполирует между шагами.
- **Только целые числа и фиксированная точка** в боевой математике.
  Плавающая точка в сетевой игре на 12 человек рано или поздно разъедется.
- Пространственный индекс (grid/quadtree) на 61 440 × 61 440 единиц —
  поиск целей перебором по 3 000 юнитам невозможен.
- Поиск пути: flow field на сетке 1920 × 1920 из `war3map.wpm`.

### 4.3 Рендер

Главное требование задают 25 222 декорации.

- **Инстансинг.** 431 тип декораций → 431 batch вместо 25 222 вызовов.
  Это и есть решение пункта 4 диагноза.
- **Frustum culling** по чанкам ландшафта.
- **LOD и потоковая загрузка**: подгружать модели по мере приближения камеры,
  а не всё при старте.
- Ландшафт 480 × 480 — чанками 32 × 32 тайла, 225 чанков.

### 4.4 Сеть

12 игроков — **lockstep**: передаются команды, а не состояние. Это единственный
вариант, который выдерживает такой объём юнитов. Прямое следствие требования
детерминизма из 4.2.

## 5. Модули

```
pipeline/     конвейер (Python) — есть
engine/
  jass/       лексер, парсер, VM, реестр хендлов
  natives/    321 функция контракта, по подсистемам
  sim/        сущности, бой, поиск пути, приказы
  render/     ландшафт, модели, эффекты, камера
  audio/      звук и музыка
  ui/         HUD, панель команд, миникарта
  net/        lockstep, синхронизация
game/         точка сборки, загрузка данных
```

Порядок реализации `natives/` — по частоте вызовов из
[`data/jass-api.json`](data/jass-api.json): сначала `player` и `unit`
(11 213 мест вызова из 15 287, то есть 73 %), потом остальное.

## 6. Выбор стека — требуется решение

Ниже честное сравнение. Рекомендация одна, но решение за владельцем проекта.

### Вариант A — TypeScript + WebGPU (рекомендую)

Хорошо:
- Один код → браузер и десктоп (Tauri/Electron). Для аудитории WC3-карт
  игра по ссылке, без установки — заметное преимущество распространения.
- В экосистеме уже есть разобранные MDX/BLP (проекты вроде `mdx-m3-viewer`) —
  форматы не придётся реверсить с нуля.
- JASS VM на динамическом языке пишется быстрее.
- Быстрый цикл разработки.

Плохо:
- Пик производительности ниже нативного. Лечится переносом горячей симуляции
  в Rust/WASM — но архитектуру под это надо закладывать сразу.
- Детерминизм требует дисциплины: только целые числа, никакого `Math.random`.

### Вариант B — Godot 4 (C#)

Хорошо: полноценный редактор, нативные сборки, физика и сцены из коробки.
Плохо: MDX и BLP придётся писать с нуля; узлы Godot тяжеловаты для 25 000
декораций — нужен `MultiMesh`, то есть в обход штатного пути; распространение
только через установщик.

### Вариант C — Rust / C++ своими руками

Хорошо: полный контроль, максимальная производительность, никаких чужих
ограничений.
Плохо: срок вырастает в разы. Всё — от загрузки текстур до UI — пишется руками.
Оправдано, только если движок сам по себе является целью.

### Рекомендация

**Вариант A**, с одной оговоркой: ядро симуляции с первого дня изолировано за
интерфейсом и не использует ничего из DOM и плавающей арифметики. Тогда перенос
в Rust/WASM останется рефакторингом одного модуля, а не переписыванием проекта.

Если для вас важнее нативная сборка и вы уверенно себя чувствуете в C# — вариант B
тоже рабочий; конвейер данных из `tools/` от стека не зависит и подойдёт любому.

## 7. Риски

| Риск | Оценка | Что делать |
|---|---|---|
| Расхождение поведения с оригиналом | Высокий | Сравнивать с записями партий в WC3 по шагам |
| Эффекты и партиклы MDX | Средний | Нет прямого аналога в glTF — описывать отдельной схемой |
| Детерминизм в сети | Высокий | Фиксированная точка с самого начала, не «потом» |
| Правовой статус ассетов | **Требует решения** | Модели и текстуры Blizzard распространять нельзя |
| Объём работ | Высокий | Порядок по контракту из 321 функции, ранний играбельный срез |

### Про ассеты отдельно

Часть моделей и текстур — собственность Blizzard, часть взята с ресурсов
сообщества у сторонних авторов. Пока проект работал как карта для WC3, вопрос
не стоял: игрок и так владел игрой. Самостоятельная сборка меняет ситуацию.

Варианты: поставлять игру без ассетов и извлекать их из установленного WC3
на стороне игрока; либо постепенно заменять на свои. Первое решает вопрос
сразу и технически несложно — конвейер уже умеет читать MPQ.

## 8. Следующий шаг

1. Зафиксировать стек (раздел 6).
2. Написать конвертеры `MDX → glTF` и `BLP → PNG/KTX2`.
3. Собрать просмотрщик мира: ландшафт + декорации, без игровой логики.
   Это проверяет весь конвейер данных на реальном объёме и даёт первую
   картинку на экране.
4. Затем JASS VM и функции контракта по убыванию частоты.
